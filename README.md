# PulseDB

A high-performance telemetry analytics platform in modern C++20 that ingests,
processes, aggregates, stores and visualizes playback events generated by
media SDKs.

```text
SDK Simulators → HTTP POST → Collector → Queue → Worker Pool
    → Aggregation Engine → Time-Series Storage → REST API → Dashboard
```

Full design: [docs/PulseDB_Project_Specification.md](docs/PulseDB_Project_Specification.md)

## Module status

| Module | Directory | Status |
| --- | --- | --- |
| Core domain types | `core/` | ✅ `EventBatch`, `EventType`, typed `Event` + parser |
| Event Queue | `queue/` | ✅ Bounded blocking queue (mutex + condition_variable) |
| Collector Server | `collector/` | ✅ HTTP ingestion (cpp-httplib), validation, backpressure |
| SDK Simulator | `sdk/` | ✅ Session generation, batching, retry + backoff, bounded offline spool + replay |
| Worker Pool | `workers/` | ✅ `hardware_concurrency()` threads draining the queue |
| Event Processor | `processor/` | ✅ Events → metrics (reusable lock-free `MetricAccumulator`) |
| Aggregation Engine | `aggregation/` | ⚠️ Per-minute bucketing + capped player/device segments + queries — correct, but does not scale with worker count (see Known gaps) |
| Time-Series Storage | `storage/` | ⚠️ Nested Y/M/D/H/Minute store, O(1) point lookup, thread-safe — but unordered and unbounded, so range queries and memory grow with uptime |
| REST API | `query/` | ✅ `MetricsApi` + `QueryServer` (CORS) on a second port |
| Persistence | `persistence/` | ✅ Durable metrics snapshot + validated restore |
| Dashboard | `dashboard/` | ✅ React + TypeScript + Recharts, live-polling (QoE + operational panels) |

### Known gaps

Being explicit about what this does *not* do yet, because the modules above
being green does not make it production-ready:

- **Ingestion does not scale with worker count.** `AggregationEngine::process()`
  takes three global mutexes per event — the time-series store's and one per
  segment map — even on the common path where the bucket already exists.
  Measured on 16 cores: **3.9M events/s on one thread, 1.9M on eight (0.49x)**.
  Adding workers past ~2 makes ingest slower. Isolating the cause (disjoint
  buckets to remove all cache-line sharing; then dropping to one mutex; then a
  bare accumulator with no mutex at 27M events/s on eight threads) shows the
  mutex costs roughly **15x** the atomic contention, so this is lock cost, not
  false sharing. Per-worker sharded accumulators merged on read is the fix and is
  the single most important outstanding item.
- **Queries contend with ingestion.** Every query holds the same store mutex for
  its whole traversal, and buckets are never evicted, so the cost grows with
  uptime: a 15-row `/metrics/live` holds the ingest lock for ~13 ms at 30 days of
  uptime and ~38 ms at 90 days. The dashboard issues four such queries every 2 s
  per open tab.
- **No retention policy.** Minute buckets are never evicted, so memory grows
  with uptime. Timestamps are bounded to a freshness window, which bounds how
  fast that can happen, but not the total.
- **No authentication and no rate limiting** on either port. Combined with
  httplib's fixed thread pool (`max(8, hardware_concurrency() - 1)`, thread per
  connection), roughly 15 slow connections can occupy the entire ingest pool.
- **Range queries are O(total buckets).** The nested-map store has no ordering,
  so `recent`/`range` materialise and sort every bucket — the `minutes`
  parameter reduces the response, not the work. A flat sorted ring buffer would
  make these O(result) *and* provide retention; that is the main planned
  refactor.
- **At-least-once delivery with no deduplication.** `RetryingSender` retries on
  transport failure, which includes a read timeout *after* the collector already
  accepted and enqueued the batch, and `SpoolingSender` will replay it. The
  aggregates are non-idempotent counters, so a redelivered batch is counted
  twice and inflates metrics permanently. There is no batch ID or dedup window.
- **No TLS**, and the SDK now *refuses* an `https://` URL rather than silently
  sending cleartext to port 443. Terminate TLS at a proxy if it is required.
- **No percentiles.** Only means are aggregated, and p50/p95/p99 startup time is
  what actually matters for playback QoE.
- **No structured logging.** The library modules do not log at all.
- **Snapshot-only durability**, with no write-ahead log: a crash loses up to
  `snapshot_interval_sec` of aggregates plus whatever is still queued.

## Running the server

```powershell
./build/collector/pulsedb_collector.exe            # reads config/pulsedb.json
./build/collector/pulsedb_collector.exe my.json    # or a custom config
```

This runs the full pipeline: the HTTP collector (`POST /v1/events`,
`GET /health`) feeds a bounded queue drained by a pool of
`workers` threads, which parse events and aggregate them into per-minute
time buckets. Live metrics (views, startup time, rebuffering, errors,
watch time, bitrate, and the number of `minutes` buckets) print every
~2 seconds. Try it:

```powershell
curl http://127.0.0.1:8080/health
curl -X POST http://127.0.0.1:8080/v1/events -H "Content-Type: application/json" `
     -d '[{\"event_type\":\"video_start\",\"session_id\":\"s1\"}]'
```

Responses: `202` accepted, `400` malformed JSON, `413` body over
`max_body_bytes`, `422` bad schema (including an unrecognised `event_type`, an
out-of-window timestamp, or an over-long label), `503` when the queue is
saturated (clients should retry with backoff).

`event_type` is checked against the ten types the pipeline understands, not just
for presence. Presence alone was the whole check, and that made the `202` a lie:
an unrecognised type was accepted, then discarded by the worker as a parse
failure, so the client was told its data was stored when it had been thrown
away — no data and no error. A typo'd or version-skewed type is precisely the
case that has to be loud, because only the sender can fix it.

### Ingest limits

Every limit below exists to bound what a single untrusted request can cost, and
each is enforced before the work it guards. Defaults in `IngestOptions`:

| Limit | Default | Why |
| --- | --- | --- |
| `max_body_bytes` | 8 MiB | Installed on the server, so oversized bodies are refused **while reading** rather than buffered first |
| `max_json_depth` | 32 | A valid batch is 2–3 levels deep; deeper input only inflates the parsed DOM |
| `max_events_per_batch` | 10,000 | Bounds per-request fan-out |
| `max_lateness` / `max_future_skew` | 7 days / 5 min | An event timestamp addresses a permanent minute bucket, so an unbounded timestamp is an unbounded allocation |
| `max_label_length` | 128 | `player`/`device` become permanent map keys |
| `max_segments_per_dimension` | 1,000 | Caps label cardinality; names beyond it fold into `__other__` so totals stay exact |
| `max_startup_time_ms` | 600,000 | See below |
| `max_buffer_duration_ms` | 3,600,000 | See below |
| `max_bitrate_kbps` | 1,000,000 | See below |
| `max_watch_time_ms` | 86,400,000 | See below |

An event with no `timestamp` is stamped with its receipt time rather than
defaulting to the epoch.

The four numeric bounds exist because each of those fields is summed into an
**unsigned** 64-bit counter that only ever grows and is never recomputed from
source. An out-of-range sample is therefore permanent corruption of an average,
not one bad data point — and a *negative* one converted to ~1.8e19 and destroyed
the metric outright. Because the poisoned value is a legitimate unsigned integer,
it also round-tripped through the snapshot and survived a restart. One
unauthenticated request was enough. Values outside `[0, max]` are now rejected
with `422`, and `MetricAccumulator` independently ignores negative samples so the
invariant holds for callers that never go through HTTP.

> **Note:** these limits live in `IngestOptions` and are **not** yet settable from
> `config/pulsedb.json` — the server constructs `CollectorConfig` without
> overriding `ingest`, so they are effectively compile-time constants. Wiring
> them through config is outstanding.

## Configuration

`config/pulsedb.json` (or a path given as `argv[1]`). Every key is optional; a
missing file falls back to the defaults below. **Unknown keys are rejected**, so
a typo fails at startup instead of silently leaving a default in place, and any
out-of-range value exits non-zero listing what was wrong.

| Key | Default | Range |
| --- | --- | --- |
| `queue_size` | `100000` | 1 – 10,000,000 batches |
| `workers` | `0` = `hardware_concurrency()` (the shipped `config/pulsedb.json` sets `8`) | 0 – 1024 |
| `host` | `"0.0.0.0"` | non-empty |
| `port` | `8080` | 1 – 65535 (ingest) |
| `query_port` | `8081` | 1 – 65535, must differ from `port` |
| `snapshot_path` | `"data/metrics.json"` | `""` disables persistence |
| `snapshot_interval_sec` | `10` | 0 – 86400 (`0` disables periodic saves) |

Note `queue_size` bounds the number of *batches*, not events or bytes — with
`max_events_per_batch` at 10,000 the queue's memory ceiling is much higher than
the count suggests. Bounding it by payload bytes is the better design and is
not done yet.

## Querying metrics (REST API)

The server also exposes a read-only metrics API on `query_port` (default
`8081`), separate from ingestion. All responses are JSON with permissive
CORS headers.

### Stall metrics: two counters, not one

`buffer_count` and `buffer_samples` count different populations and are both
exposed, because conflating them was a real bug:

| Field | Counts | Source event |
| --- | --- | --- |
| `buffer_count` | Stalls that **began** | `buffer_start` |
| `buffer_samples` | Stalls that **finished** with a measured duration | `buffer_end` |
| `buffer_avg_ms` | `buffer_duration_ms_sum / buffer_samples` | — |

`buffer_avg_ms` used to divide by `buffer_count`, mixing the two. A stall that
began in one minute and ended in the next put the count in bucket A and the
duration in bucket B, so **both** minutes reported `buffer_avg_ms = 0` and the
measured stall time was invisible in each — and globally the mean was biased low
by every session abandoned mid-stall. Given stalls of 200–3,000 ms and segments
advancing 5–30 s, boundary-crossing stalls are common, not exotic.

A stall is attributed to the minute in which it **ended**, which is where its
duration sample lands. Re-attributing it to its start minute needs per-session
state and is not done.

| Endpoint | Returns |
| --- | --- |
| `GET /metrics` | Platform-wide totals + minute-bucket count |
| `GET /metrics/live?minutes=N` | The N most recent per-minute buckets (N clamped to `max_response_minutes`) |
| `GET /metrics/range?from=<ms>&to=<ms>` | Buckets within an epoch-ms window (`400` if the window exceeds `max_response_minutes`) |
| `GET /metrics/player` | Per-player metric breakdown |
| `GET /metrics/device` | Per-device metric breakdown |
| `GET /status` | Live operational metrics: events/sec, queue depth, active sessions, error rate, CPU %, memory, uptime |

#### Response-size bound

Both bucket endpoints took an unbounded window, so one short unauthenticated GET
could ask the server to serialise its entire store — measured at 5,000 buckets,
`?minutes=999999999` turned a ~60-byte request into a **1.25 MB** response
(~20,000x amplification), holding the store mutex the ingest path also needs for
the whole traversal. Since buckets are never evicted, that grew with uptime.

`QueryServer::Config::max_response_minutes` (default **1,440** — a day of
minutes) now bounds it: `/metrics/live` clamps `minutes`, and `/metrics/range`
rejects an over-wide window with `400` rather than truncating, because a partial
slice would read as "these are all the buckets in that window". The shipped
dashboard asks for 15, so nothing legitimate is affected. Note this bounds the
*response*, not the *work* — `recent`/`range` still traverse every bucket (see
"Known gaps"), and the port still has **no authentication and no rate limiting**.

```powershell
curl.exe http://127.0.0.1:8081/metrics
curl.exe "http://127.0.0.1:8081/metrics/live?minutes=10"
curl.exe http://127.0.0.1:8081/metrics/player
```

## Persistence

Metrics survive a restart. The server periodically snapshots the aggregate
state (every minute bucket plus the player/device segments, as raw counters)
to `snapshot_path` (default `data/metrics.json`) every `snapshot_interval_sec`
seconds, and once more on a clean shutdown. On startup it reloads that
snapshot, so totals and time-series pick up where they left off. Set
`snapshot_path` to `""` to disable.

Writes are durable and atomic: the snapshot is written to a temp file, verified,
flushed to stable storage, and only then renamed over the previous one, so a
failure partway through (a full disk, most obviously) leaves the last good
snapshot intact rather than replacing it with a truncated one. Restores are
all-or-nothing and version-checked, so a corrupt file is rejected outright
instead of leaving half a snapshot applied.

The on-disk format is at **version 2**, which added `buffer_samples`. Version 1
files still load: the counter it does not carry restores as 0, so mean stall
duration reads as "no data" for those buckets rather than a number derived from
the mismatched denominator v1 was using. That keeps history across the upgrade
instead of discarding it. Absence is tolerated *only* for counters introduced
after the file's own version — a v1 file missing a v1 counter is still rejected.

Combined with the SDK's bounded offline spool + replay, this makes most of an
outage survivable — but **not lossless**, and it is worth being precise about
the limits:

- A server crash loses up to `snapshot_interval_sec` of aggregates plus
  everything still sitting in the in-memory queue. There is no write-ahead log.
- The SDK's spool is capped (default 1,000 batches) and evicts oldest-first, so
  a long outage costs the oldest data rather than the client's disk.

Configuration is validated at startup and the server exits non-zero on any bad
value, rather than silently falling back to defaults.

## Benchmarks

Throughput suites live in `benchmark/` (opt-in), using a small dependency-free
harness rather than Google Benchmark, which does not compile against this MinGW
distribution's COM/OLE headers. Build and run them with:

```powershell
./scripts/bench.ps1
```

Representative results on the development machine (Release, GCC 16),
single process — absolute numbers vary by hardware, the *shape* is the point:

| Suite | Result |
| --- | --- |
| Queue push+pop, 1 thread | ~18–24M items/s (~45–55 ns/item) |
| Queue MPMC, 1→8 producer/consumer pairs | ~4.5M → ~1.5M items/s |
| Aggregation fold, 1 thread | ~2.5–3.0M events/s (~350–420 ns/event) |
| Ingest validation (JSON → EventBatch) | ~190K–460K events/s, ~27–64 MB/s |

Two honest observations the numbers surface:

- **Aggregation does not scale, and the cause is lock cost, not false sharing.**
  An earlier version of this section attributed the flat curve to atomic
  cache-line contention on `MetricAccumulator`. That was wrong by roughly 15x.
  The discriminating experiment varies sharing and synchronisation
  independently — 400k events/thread, 16 cores:

  | Scenario | 1 thread | 8 threads |
  | --- | --- | --- |
  | Engine, shared buckets + segments | 3.52M/s | 1.75M/s |
  | Engine, **disjoint** buckets + segments (no accumulator shared between threads) | 3.53M/s | 1.45M/s |
  | Engine, disjoint buckets, **no segment labels** (1 mutex instead of 3) | **7.23M/s** | 2.30M/s |
  | Bare shared `MetricAccumulator`, **no mutex at all** | 48.1M/s | **27.0M/s** |

  These are single runs, so read the **ratios between rows**, not the digits;
  repeating the experiment moves each figure by a few percent and changes none of
  the conclusions.

  Row 2 vs row 1: removing all cross-thread cache-line sharing does not help.
  Row 3 vs row 2: removing two of the three mutexes doubles single-thread
  throughput. Row 4: the pure false-sharing ceiling is 27M events/s, far above
  what the engine reaches. The store mutex is the bottleneck. Padding
  `MetricAccumulator` (80 bytes, ten adjacent atomics, no padding — measured) is
  still worth doing, but only after the mutex leaves the hot path, and its
  effect is second-order.
- The **queue** is the spec's *Version 1* (mutex + condition_variable), and
  per-item throughput drops as producer/consumer pairs grow. This is *not*
  currently a bottleneck and the lock-free *Version 2* is not the right next
  move: the queue carries **batches**, so at 10,000 events/batch and 1M events/s
  it takes ~100 lock acquisitions per second, against ~3 million per second in
  the aggregation engine. Fixing aggregation first is worth orders of magnitude
  more than replacing the queue.

What these numbers are **not**, so they are not over-read:

- **Throughput only, no latency distribution.** The `ns/item` column is
  `1 / throughput`, not a measured latency, and there are no p50/p99/p999
  figures. For an ingest path the tail is the number that matters, so this is
  the most important gap in the methodology.
- **Single timed run, no warmup and no repetition**, so there is no variance
  and any delta under ~10% is noise.
- **Ingest validation is not end-to-end ingest.** That row measures
  `IngestHandler` alone, on a body already hot in cache — no socket, no queue,
  no worker, no aggregation. There is no end-to-end throughput number, and the
  `--live` SDK mode cannot produce one: it sends one batch per 150 ms tick
  synchronously on a single thread, so it is a demo traffic generator, not a load
  generator.
- **Only 15 minute buckets are exercised**, so the benchmarks never show the
  effect that dominates a long-running server: query cost grows with bucket
  count, from 0.01 ms at 60 buckets to 38 ms at 129,600 (90 days).
- **No memory or CPU measurement**, despite `SystemStats` already implementing
  both for `/status`.

## Continuous integration

[.github/workflows/ci.yml](.github/workflows/ci.yml) runs on every push to
`main` and on pull requests:

- **Build & test (Linux, GCC 14)** — configures with CMake/Ninja, builds all
  modules, and runs the full test suite via `ctest`.
- **Build dashboard (Node)** — `npm ci` then `npm run build` (type-check +
  bundle).

The workflow activates automatically once the repository is pushed to GitHub:

```bash
git remote add origin git@github.com:<you>/PulseDB.git
git push -u origin main
```

Note the `push` trigger is **`main`-only**, so pushing a feature branch on its own
runs nothing — open a pull request, or use the **Run workflow** button on the
Actions tab (`workflow_dispatch`), rather than reading the absence of a run as a
broken pipeline.

CI gaps worth knowing about, since one of them has already cost a real bug:

- **Linux/GCC only.** Development happens on Windows/MinGW, which CI never
  builds. That is precisely how a `std::shared_mutex` defect went unnoticed:
  libstdc++ forwards `lock_shared()` to `pthread_rwlock_rdlock`, which on
  winpthreads intermittently fails to acquire, so readers ran concurrently with
  an inserting writer and corrupted the store (wrong bucket counts, lost
  increments, and heap corruption in 7 of 40 stress runs; 0 of 40 with
  `std::mutex`). glibc is unaffected, so CI was green throughout.
- **No sanitizers.** No TSan, ASan, or UBSan job, which is the largest testing
  gap for a project whose central claim is thread safety.
- **Benchmarks are not built** (`PULSEDB_BUILD_BENCHMARKS` is off), so they can
  rot silently.
- **No `-Werror`**, so warnings do not fail the build. The tree is currently
  warning-free under both GCC 14 (`-Wall -Wextra -Wpedantic`, verified in the
  container build) and the MinGW toolchain, but nothing enforces that it stays
  that way — and the two toolchains do not report the same warnings, so
  "clean locally" was not evidence of "clean in CI".

## Docker

A multi-stage [Dockerfile](Dockerfile) builds the server on Ubuntu + GCC 14
and ships a slim runtime image (static libstdc++, so it needs only glibc).

```bash
# with docker compose
docker compose up --build          # ingest :8080, metrics API :8081

# or plain docker
docker build -t pulsedb .
docker run --rm -p 8080:8080 -p 8081:8081 pulsedb
```

Then point traffic and the dashboard at the published ports, e.g.
`./build/sdk/pulsedb_sdk.exe --url http://localhost:8080` and the dashboard at
`http://localhost:8081`.

The runtime image runs as the unprivileged user `pulsedb` (uid 10001, outside the
distro's system range so it cannot collide with a host account behind a bind
mount) and declares a `HEALTHCHECK` against `GET /health`, probed with a bash
`/dev/tcp` redirect rather than by installing `curl` — an HTTP client in a runtime
image is a fetch-and-execute primitive, and this needs no extra package.

`docker compose` mounts a named volume at `/app/data`, which is where
`snapshot_path` resolves. Without it the snapshot would live in the container's
writable layer: it would survive `docker restart` but be destroyed by
`docker compose up --build` — the very command above — so persistence would look
broken when it was not. The compose service also sets `mem_limit: 2g`, because
minute buckets are never evicted (see “Known gaps” above) and a container restart
is a better failure than taking the host down.

## Running the SDK simulator

With the collector running, generate realistic playback traffic:

```powershell
./build/sdk/pulsedb_sdk.exe --url http://127.0.0.1:8080 --sessions 50 --batch-size 40
```

Flags (all optional): `--url`, `--sessions`, `--batch-size`, `--seed`
(fixed seed => reproducible sessions), `--delay-ms` (pause between sessions).
Each session is a realistic event sequence (`video_start` →
`startup_complete` → bitrate changes / rebuffering / pause / seek →
`playback_end`); batches are POSTed with automatic retry + exponential
backoff on transient failures.

If the collector is unreachable after all retries, batches are **spooled to
disk** (`--spool-dir`, default `spool/`) instead of being lost, and
**replayed** automatically on the next run once the collector is back. The spool
is capped (default 1,000 batches) and evicts oldest-first, so a long outage costs
the oldest data rather than the client's disk — **bounded loss, not zero loss**.
Retries are jittered so a fleet of clients does not resynchronise into waves
against a collector that has just come back up.

### Live mode (for a continuously-updating dashboard)

Batch mode ships each session complete (start→end) in a burst, so the
server's live gauges (events/sec, **active sessions**) barely move and drop to
zero once the burst ends. For a dashboard that stays alive, use `--live`,
which keeps sessions genuinely open — it maintains N concurrent sessions,
emitting each one's events over real time and replacing sessions as they
finish:

```powershell
./build/sdk/pulsedb_sdk.exe --live --concurrency 30
# runs until Ctrl+C; add --duration-sec N to stop automatically
```

With this running, `GET /status` shows `active_sessions ≈ 30` and a steady
`events_per_sec`, and the dashboard's "Live operations" tiles stay populated.
